# 워커 수와 자원 검증

역할 수와 동시 실행 워커 수는 독립 설정이다. 기존 `demo --workers N` 및 `Pool.Workers`는 1..64를 지원한다. 측정 결과를 반영하는 것은 이번 검증용 추천기이며, 실행 중 자동 확장·축소를 추가한 것은 아니다.

## 재현

Go 1.26.11, Node와 pi 잠금 의존성, Python 3 표준 라이브러리가 필요하다. 실제 pi 프로세스를 쓰되 합성 모델과 합성 도구만 실행한다.

```sh
./scripts/go.sh build -o bin/role-runtime ./cmd/role-runtime
python3 scripts/benchmark.py --plan matrix --output artifacts/resource-matrix.json
python3 scripts/benchmark.py --plan extended --output artifacts/resource-extended.json
```

macOS/Linux의 `ps`로 자식 프로세스 트리를 측정한다. 제한된 샌드박스에서는 프로세스 조회 권한이 필요하다. 계측기는 PID·부모 PID·RSS·누적 CPU 시간만 조회하고, 테스트 프로세스 트리의 수치만 보존한다. 다른 프로세스의 명령줄·환경변수는 수집하지 않는다. 측정 중 다른 테스트나 빌드를 동시에 실행하지 않는다.

- `matrix`: 40역할×10회, 100역할×4회, 400역할×1회로 총 400작업을 유지한다. 400역할은 워커 1·2·4·8·12개에서 각각 두 번 실행하며 순서를 고정 시드로 섞는다.
- `extended`: 400역할×2회와 40역할×20회에 작업당 4KiB 입력을 넣어 재방문·누적 기록을 확인한다. 같은 80작업의 프로세스 재사용/작업별 새 프로세스 비교와 도구 대기 250ms의 워커 수 비교도 수행한다.
- `wait`: 250ms 도구 대기를 워커 1·2·4·8개에서 비교한다. `--workers 2`처럼 선택한 계획의 워커 수를 필터링할 수 있다. 이번 결과에서는 extended의 1·4·8개에 `--plan wait --workers 2`를 추가했다.
- 모든 경우 큐 크기는 32로 고정한다. 매 실행에 새로운 임시 상태를 만들며 결과·역할 지침·도구·이전 라운드 기록 검사는 그대로 유지한다.

역할 수 비교는 총 작업 수를 고정하지만 역할당 기록 길이는 달라진다. 역할 정의 개수만 바꾼 완전한 단일 요인 실험은 아니다. 합성 도구 정의도 역할 수만큼 등록되므로 그 비용이 포함된다. extended의 4KiB는 토큰 수가 아니라 문자열 바이트 수다.

## 지표 정의

- 전체 시간과 처리량: 프로세스 실행부터 종료까지. 역할 정의 저장, 워커 시작, 실행, 정리 포함.
- Pool 처리량: 역할 정의 저장 이후, 워커 시작부터 종료까지의 별도 값.
- 실행 p50/p95: Executor.Execute 진입부터 반환까지. 역할 복원·RPC·도구 실행 포함, 큐 대기와 작업 접수/결과 fsync는 제외한다. 전체 요청 지연으로 해석하지 않는다.
- Peak tree RSS: 0.2초 간격으로 관측한 Go와 모든 하위 프로세스 RSS 합의 최댓값. 공유 페이지 중복 합산 가능성이 있고 순간 피크는 놓칠 수 있다. 정확한 물리 메모리 사용량이나 cgroup 제한값은 아니다.
- CPU seconds: 각 PID에서 관측한 최대 누적 CPU 시간의 합. 종료 직전 샘플을 놓칠 수 있어 하한 추정이다. 특히 짧게 생성·종료되는 비교군은 오차가 크다.
- Mean CPU cores: sampled CPU seconds / 전체 경과 시간. 1.0은 평균적으로 논리 CPU 하나를 사용한 양이며, 모든 코어를 합쳐 100%로 정규화한 값이 아니다. CPU 순간 부하나 시스템 전체 사용률이 아니다.

관측 간격은 `--interval`로 조정한다. 최대 프로세스 수와 초당 RSS 시계열도 결과에 보관한다. 검사 자체의 CPU는 측정 트리에 포함되지 않지만 같은 장비에 부하를 주므로 완전히 무관측 상태의 성능은 아니다.

## 추천 계산

설정 가능한 예산:

```sh
python3 scripts/benchmark.py --plan matrix \
  --memory-budget-mib 4096 --cpu-budget-cores 6
```

기본값은 장비 총 메모리의 25%, 논리 CPU 수의 50%다. 현재 사용 가능한 여유 자원을 탐지한 값이 아니라 다른 프로그램을 위한 여유를 남기는 명시적 정책이다. 운영 환경에서는 실제 자원 할당량으로 지정해야 한다.

1. 각 워커 수의 반복 측정 처리량 중앙값을 계산한다.
2. 반복 측정 중 가장 큰 RSS 및 가장 큰 평균 CPU 사용량이 예산을 넘으면 제외한다.
3. 남은 후보 중 최고 처리량의 95% 이상을 내는 가장 작은 워커 수를 선택한다.
4. 예산에 맞는 후보가 없으면 추천값을 비워 둔다. 측정하지 않은 수를 외삽하지 않는다.

이 규칙은 처리량과 자원 비용의 절충점이다. 실제 모델의 API 동시 요청 제한·토큰 속도·요금·도구 부하·요청 지연 SLO를 반영한 전역 최적값은 아니다. 두 번의 반복은 탐색용이며 차이가 작으면 추가 반복이 필요하다. 최고값이 탐색 상한에 있으면 그 이상도 검증해야 최적점을 주장할 수 있다.

역할별 400개 프로세스를 실제로 상주시킨 비교는 수행하지 않는다. 단순 곱셈으로 그 구성의 메모리 절감률을 검증했다고 표현하지 않는다. 페이징을 통한 모델 컨텍스트 확장도 이 실험 범위 밖이다.
