# Heartbeat와 역할 메일박스

사용자와 합의한 구분: 직선형 작업열의 결과 전달을 넘어 역할들이 서로 요청·대기·재개하는 파이프라인에는 heartbeat와 영속 메일박스가 중요한 기반이다.

현재 Go RPC/40-role/4-worker 검증 다음에 최소 협업 제어 기능을 추가한다. 이번 구현에 완성된 heartbeat·SMS 기능이 있다고 표현하지 않는다.

- 메시지 주소는 워커 ID가 아니라 **프로젝트 + 역할 인스턴스**다. 역할 버전 호환 정책도 정의해야 한다.
- 비활성 역할의 메시지도 저장하고, 역할 활성화 시 필요한 메시지만 읽는다.
- 요청 ID, 응답 상관관계, 처리 상태와 중복 처리 정책이 필요하다.
- 답을 기다릴 때 상태를 저장하고 워커 슬롯을 반환한다. 응답 도착 시 외부 작업 공급자에 재개 가능 이벤트를 전달한다.
- 워커 heartbeat는 프로세스 응답성, 작업 진척 이벤트는 실제 진행을 나타낸다. heartbeat만으로 무한 루프를 정상 작업으로 판단하지 않는다.
- 역할마다 heartbeat 루프나 상주 프로세스를 만들지 않는다. 감독 계층에서 활성 워커만 관찰한다.

후속 수용 기준: **네 워커 모두 다른 역할에 요청하고 대기하더라도 슬롯이 반환되어 응답 작업이 실행되고, 응답 후 기존 작업이 재개된다.** 메시지 유실·중복·재시작 시 복원도 검사한다. 이 시나리오를 통과하기 전까지 자유로운 역할 간 협업 파이프라인을 완성했다고 보지 않는다.

Heartbeat 만료는 장애 의심 신호이지 이전 실행이 종료되었다는 증거가 아니다. 재할당에는 실행 임대와 세대 번호(fencing token)를 두어 오래된 워커의 결과를 거절해야 한다. 외부 도구 부작용에는 별도 멱등성 정책이 필요하다.

최소 상태 전이는 `ready → running → waiting → ready → running → completed`다. `waiting` 진입 시 체크포인트·대기 조건을 기록하고 슬롯을 반환한다. 메시지가 대기 등록보다 먼저 도착해도 놓치지 않도록 영속 inbox 확인과 대기 등록의 원자성을 설계한다. 메시지 저장 후 알림 전달에 실패해도 재탐색할 수 있어야 한다.
