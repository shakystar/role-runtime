# 실행 모델 초안

상태: 제안. 하네스의 실제 전환·복원 능력을 확인한 후 인터페이스를 고정한다.

## 책임 분리

외부 작업 공급자는 작업의 목적, 역할, 입력, 의존성 충족 여부를 결정한다. 런타임은 실행 가능 여부와 자원 한도를 확인하고 빈 워커에 작업을 배치한다. LLM을 이용한 업무 계획·역할 선정은 런타임의 필수 기능이 아니다.

| 구성요소 | 책임 |
| --- | --- |
| Admission | 용량·계약 검증, 중복 작업 ID 처리, 초과 입력에 backpressure 적용 |
| Role registry | 역할 정의와 버전 조회 |
| State store | 프로젝트·역할 인스턴스별 상태 및 작업 체크포인트 보존 |
| Context assembler | 필수 지침과 현재 작업, 필요한 기억·자료를 예산 안에서 구성 |
| Worker pool | 최대 K개 실행, 취소, 회수, 역할 전환 |
| Harness adapter | 역할 적용, 실행, 이벤트, 취소 완료 확인, 지원 범위 내 재개 |
| Artifact store | 결과물을 저장하고 다음 단계에 참조 전달 |

이 구성요소들은 논리적 경계이며 초기부터 별도 서비스로 분리하지 않는다.

## 저장되는 것

- `RoleDefinition`: ID, 버전, 지침, 도구 정책, 출력 계약, 모델 제약.
- `RoleState`: project ID, role instance ID, role version, revision, 기억 참조.
- `Task`: ID, project ID, role 참조, 입력 참조, 실행 상태, 시도 번호.
- `Checkpoint`: task ID, adapter/version, 재개 자료 참조, 완료된 실행 경계.
- `ContextManifest`: 사용한 역할·상태 revision, 자료 ID, 크기/토큰 계산 방식.

역할 ID만으로 기억을 조회하지 않는다. 서로 다른 프로젝트나 같은 역할의 독립 인스턴스가 섞이지 않아야 한다. 모델의 숨겨진 내부 상태는 이 스키마에 포함된다고 가정하지 않는다.

## 전환 순서

1. 외부 작업을 수신하고 실행 슬롯과 상태 소유권을 확보한다.
2. 지정된 역할 버전과 프로젝트별 상태를 조회한다.
3. 필요한 자료만 가져와 예산 안에서 컨텍스트를 구성한다.
4. 워커의 이전 실행이 종료됐는지 확인하고 이전 메시지·도구·리소스 참조를 해제한다.
5. 역할의 지침, 도구, 작업 디렉터리 등 실행 범위를 적용한다.
6. 하네스를 실행하고 이벤트를 제한된 버퍼로 처리한다.
7. 안전한 실행 경계에서 결과와 상태를 커밋하고 워커를 반환한다.

4~5번을 지원하지 않는 하네스는 프로세스 재생성 또는 SDK 래퍼를 비교한다. 이를 지원하는 것처럼 숨기거나 과거 대화에 새 역할 지침만 덧붙여 전환으로 간주하지 않는다.

## 실패와 취소

취소 요청 전달과 실제 도구/프로세스 종료는 다르다. 종료 확인 전에는 해당 슬롯을 다른 작업에 재할당하지 않는다. 재시작 시 실행 중이던 작업을 식별하고 하네스의 복원 능력에 맞춰 재개 또는 재시도한다.

초기 복구 모델은 재실행 가능성을 인정한다. 외부 부작용에 exactly-once를 주장하지 않는다. 작업 ID, 시도 ID, 도구 호출의 idempotency key 또는 중복 확인 절차를 검토한다. 상태 저장과 결과 기록은 원자적 갱신 또는 복구 가능한 기록 방식으로 연결한다.

## 메모리 경계

가설은 `활성 메모리 ≈ K × 활성 작업 크기 + 제한된 큐·캐시 + 하네스 기본 비용`이다. 실제 OS 메모리 반환 시점이나 캐시 비용은 측정해야 한다.

전체 작업 그래프·대화·산출물을 한번에 로드하지 않는다. 출력과 이벤트를 무제한 수집하지 않는다. 비활성 상태는 저장소에 남긴다. Go heap만 측정해서 하위 하네스 메모리를 누락하지 않는다.

컨텍스트 예산과 프로세스 RAM은 다른 지표다. 필수 규칙과 현재 작업을 우선하고 선택 자료는 명시적 정책으로 제외한다. 문자/바이트 크기를 실제 토큰 수로 표기하지 않는다.

## Sprint 2 구현 경계

`engine.Resolver`가 프로젝트·역할·버전·인스턴스별 활성화 정보를 구성하고, `engine.Pool`이 외부에서 받은 작업을 제한된 큐와 K개 워커로 실행한다. `piadapter.Adapter`는 워커별 pi RPC 프로세스를 재사용한다. 이후 페이징은 Resolver 뒤에서 별도로 실험한다.

파일 저장소는 역할/프로젝트 정의, pi 세션, 작업 접수·결과 기록, 불확실한 세션 표식을 분리한다. 같은 논리 세션은 직렬 실행한다. 큐 상한은 4096개, 작업 입력은 64KiB, 결과 텍스트는 256KiB, RPC 레코드는 기본 1MiB, 세션 파일은 16MiB로 제한한다. 이는 전체 RSS나 모델 토큰 예산을 보장하는 상한이 아니다.

현재 프로세스 소유 잠금은 macOS/Linux를 지원한다. 큐 자동 복구와 안전한 부작용 재시도는 미구현이다. 완료되지 않은 접수 기록을 무조건 재실행하지 않는다. 실행 중 취소는 abort와 완료 대기를 시도하고, 응답이 없으면 프로세스 그룹을 종료해 회수한다. 불확실한 세션은 이후 사용을 거절한다.

협업 파이프라인을 위한 heartbeat·영속 inbox·대기/재개와 임대 세대 번호는 [다음 증분](messaging-backlog.md)이다.
