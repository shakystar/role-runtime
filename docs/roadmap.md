## Sprint 1 — 재사용 가능성

목표: 기존 하네스에서 역할 교체·복원이 가능한지 확인한다.

산출물: 버전/라이선스 표, 두 후보의 최소 실행 실험, 실제로 보장 가능한 어댑터 계약, 채택 ADR.

종료 기준: A → B → A 결과와 역할·도구·상태 격리 증거가 있고, 미지원 항목 및 프로세스 재시작 필요 여부를 설명할 수 있다. 두 후보가 모두 부적합하면 자체 하네스의 최소 필요 범위를 결정한다.

## Sprint 2 — 제한된 실행 코어

목표: 외부에서 지정된 역할을 K개 워커로 실행한다.

산출물: 작업 계약, fake executor, 역할 저장소, 상태 저장, 동시 실행 제한, 선택한 하네스 어댑터.

종료 기준: 역할 40개·K=4에서 실행 수와 격리를 지키고 큐·출력 버퍼가 제한된다. 역할 수만큼 상주 실행 인스턴스를 만들지 않는다.

## Sprint 3 — 자원·비용 검증

목표: 역할 교체의 이점과 비용을 비교군 B0/B1과 비교한다.

산출물: 재현 가능한 합성 벤치마크, 전체 프로세스 메모리와 지연 보고서, 제한된 실제 모델 실험.

종료 기준: 측정 결과로 가설 유지·수정·기각을 결정한다. 기존 하네스에 비해 이점이 없으면 범위를 재설정한다.

## Sprint 4 — 복구와 기억 구성

목표: 중단·재시도 시 상태를 보존하고 필요한 기억을 선택한다.

산출물: 실패 주입, 중복 처리 정책, 체크포인트 버전 정책, 단순 상태 저장 대비 Letta 등 메모리 계층 비교.

종료 기준: 작업 유실 여부와 부작용 중복 처리 결과를 설명하고, 기억 검색이 작업 정확성과 비용에 미치는 영향을 별도로 측정한다.

## Sprint 5 — 실제 개발 작업 MVP

목표: DTO → 컨트롤러 → 픽처 → QA 같은 외부 지정 작업열을 실행한다.

산출물: CLI 또는 최소 API, 상태 조회, 합성 프로젝트 기반 end-to-end 데모, 운영 문서.

종료 기준: 실행 중단 후에도 프로젝트 작업을 이어가고 결과물의 자동 검증을 통과한다. 작업 자동 분해·웹 UI·분산화는 결과를 보고 다음 백로그로 결정한다.
