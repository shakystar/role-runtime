# ADR 0001 — Go 런타임과 하네스 재사용 검증

- 날짜: 2026-11-17
- 상태: 방향 채택. 하네스 선택은 [ADR 0002](0002-pi-first-adapter.md)에서 구체화. 저장소 선택은 미정.

## 배경

목표는 수십 개의 전문 역할을 소수의 실행 워커에 다중화하는 것이다. 작업 선택과 역할 지정은 외부 책임이다. 워커 풀과 컨텍스트 상태 수명 관리가 제품의 검증 대상이며 모델 호출·도구 루프 자체의 재작성은 목표가 아니다.

## 결정

1. 핵심 런타임의 우선 구현 언어로 Go를 선택한다.
2. 첫 스프린트에서 Go + pi RPC와 Go + Eino를 비교한다.
3. MemGPT/Letta는 실행기 선택과 구분하여 기억 관리의 재사용 후보로 평가한다.
4. 상태 저장소는 초기 단일 머신 운영을 기준으로 검토하되 아직 의존성을 확정하지 않는다.
5. 먼저 라이선스·공개 인터페이스를 조사하고 작은 실험으로 전환 능력을 확인한다. 초기부터 포크하거나 하네스 전체를 재작성하지 않는다.

## 이유와 대안

Go의 동시성 구성요소는 워커와 취소·이벤트 처리의 후보 구현에 적합하다고 판단했다. 다만 언어 선택만으로 메모리 개선이 보장되지는 않는다. 하네스 프로세스와 모델 컨텍스트 비용을 함께 측정한다.

Rust는 메모리 제어와 런타임 요구가 실제 병목으로 확인되면 재검토한다. TypeScript 내부 pi SDK 방식도 RPC 전환의 제약이나 메모리 비용 때문에 더 유리하다면 비교 대안으로 남긴다. Python은 이번 실행 코어의 우선 언어로 선택하지 않는다.

## 결과

Go와 Node 계열 프로세스를 함께 운영할 가능성이 있다. 어댑터를 두되 하네스마다 다른 체크포인트 의미를 억지로 동일하게 만들지 않는다. 지원하지 않는 기능은 명시적으로 표시한다.

Go 도구체인·의존성·프로젝트 라이선스는 아직 고정하지 않았다. 자체 하네스가 필요하다는 결정도 내리지 않았다.

## 재검토 조건

- 동일 워커의 역할 교체와 상태 격리를 기존 하네스로 구현할 수 없음.
- 프로세스 재사용 비용이 단순한 동시 실행 제한보다 불리함.
- 후보 라이선스나 배포 방식이 프로젝트 요구와 맞지 않음.
- 실제 측정에서 Go 관리 계층의 성능·메모리 한계가 드러남.

근거와 검증 항목은 [재사용 조사](../research/reuse-candidates.md) 및 [검증 계획](../validation.md)을 따른다.
