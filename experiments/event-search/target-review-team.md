# 타겟 재심 팀 실험

## 오케스트레이터와 팀의 책임

사용자 지침에 따라 오케스트레이터는 작업 의존성·권한·동시성·검증을 관리한다. 국내·국제 타겟 중 무엇을 선택할지, 어떤 제품이나 다음 실험이 적합한지는 팀이 근거를 검토해 결정한다. 이전 검색 결과와 특정 타겟을 지지하는 결론을 입력하지 않는다.

주제는 경주 여행에서 숙소 유형·지역 특성과 관광·여가·주거 분포를 파악하는 문제다. 이 문제가 실제로 중요한지부터 검토한다. 일정 생성, 선호 조율 또는 국제 타겟 채택을 전제로 하지 않는다.

## 역할과 의존성

| 역할 | 작업 | 도구 |
| --- | --- | --- |
| 조사 설계 | 양쪽 가설, 조사 방법, 반증·판정 기준 설정 | advisory |
| 국내 고객 조사 | 설계에 따라 국내 사례·반대 근거·기존 수단 조사 | web-research |
| 국제 고객 조사 | 설계에 따라 국제 사례·반대 근거·기존 수단 조사 | web-research |
| 데이터 실사 | 두 조사를 함께 읽고 실제 자료 확보 가능성 검토 | web-research |
| 반대 검토 | 원 출처와 전 단계 문서를 보고 편향·누락·대안 점검 | web-research |
| 의사결정 | 타겟 유지·수정·보류와 다음 최소 실험 결정 | advisory |

```text
              ┌ 국내 고객 조사 ┐
조사 설계 ────┤                ├─ 데이터 실사 ─ 반대 검토 ─ 의사결정
              └ 국제 고객 조사 ┘
```

고정 역할 6개를 최대 2개 실행 워커에 배정한다. 후속 역할을 먼저 대기시킨 후 설계를 실행하고, 국내·국제 조사는 설계 SMS를 받아 각각 재개한다. 동시 실행 여부는 실제 실행 구간으로 확인하며, 설정한 워커 수만으로 병렬 실행 성공을 주장하지 않는다.

엔진의 대기는 한 번에 한 발신자를 지정한다. 데이터 역할은 아직 완료되지 않은 직접 선행 역할을 차례로 기다릴 수 있다. 먼저 도착한 다른 역할의 SMS는 영속 메일박스에서 후속 대기에 사용할 수 있다. 이번 실험은 일반적인 다중 조건 대기 API를 엔진에 추가하는 것이 아니다.

## 근거 보존

역할의 완성 문서를 별도 불변 파일로 보존하고 SMS에는 문서 참조와 해시를 전달한다. 다음 실행 입력에는 완료된 선행·상위 문서 원본과 출처 목록을 함께 구성한다. 중간 모델이 요약에서 출처를 누락하더라도 원 문서를 다시 확인할 수 있어야 한다.

문서 파일 생성만으로 후속 역할에 공개하지 않는다. 해당 작업의 영속 완료 기록과 파일 본문이 일치해야 읽을 수 있다. 중단되어 파일만 남은 상태는 완료 근거가 아니다. 모델이 제출한 수신자와 의존성을 검증한 뒤 호스트가 파일·해시와 알림 본문을 연결한다.

직접 선행 문서의 요약을 다음 역할이 정확히 반영했는지 검사하고, 최종 심의 입력에 모든 선행 출처가 유지되는지도 확인한다. 이는 전달 검증이며 내용의 진실성을 자동 보증하지 않는다. 웹 도구 호출, 원문 접근 수준, 자료 행 확보, 사업 판단은 별도 결과로 기록한다.

이번 고정 팀에 필요한 제한된 문서 전달 계층이다. DB 페이징, 분산 트랜잭션, 일반 목적 문서 검색 또는 자동 작업 분해 구현이라고 주장하지 않는다.

문서 하나는 8KiB, 합성 입력은 40KiB, 실제 Execution 인코딩은 64KiB로 제한한다. 문서 각각이 상한을 만족해도 합계가 상한을 넘을 수 있다. 이때 조용히 요약·절삭하지 않고 실행을 실패 처리한다. 실행별 입력 감사 기록은 최대 128개이며 문서 참조·해시·출처 수를 남긴다.

## 판정 원칙

- 공개 자료만 조사하고 로그인·키 발급·외부 연락·게시를 수행하지 않는다.
- 게시글 표본, 검색 실패, 국내·국제 표본의 비교 가능성, 기존 서비스로 해결된 사례를 구별한다.
- 데이터 설명과 실제 행 확보를 구별한다. 부족한 근거는 보류 사유가 될 수 있다.
- 시간 경과만으로 모델 턴을 중단하지 않는다. heartbeat·출력·웹 완료·오류를 감시한다.
- 원시 문서·세션은 ignored artifacts에 보존하고 공개 문서에는 비식별 지표와 결과 요약을 기록한다.

## 실행

```sh
./scripts/go.sh build -o bin/codex-target-review ./cmd/codex-target-review
mkdir -p artifacts
./bin/codex-target-review \
  --state artifacts/target-review-new \
  --workers 2 \
  > artifacts/target-review-report.json \
  2> artifacts/target-review-monitor.jsonl
```

Codex 로그인과 네트워크가 필요하다. 기본 모델은 설치 설정을 따르며 `--state`는 새 경로여야 한다. 기존 자료 파일을 주입하는 옵션은 없다. `--workers 1`은 동일 작업열의 순차 실행에 사용할 수 있다. `researchOverlap`은 성공한 국내·국제 모델 turn의 시간 구간 중첩이며 웹 요청의 정확한 동시성 또는 처리량 이득을 뜻하지 않는다.

공개 저장소의 이 변경은 실행기와 검증 실험이다. 여행 제품의 수집기·DB·지도·사용자 화면을 구현할 별도 저장소는 아직 생성하지 않았다.

## 실패 기록

첫 실행(`target-review-01`)은 85.65초에 실패했다. 후속 역할 5개의 대기를 확인한 다음, 설계 역할이 `limitations`를 문자열 배열 대신 단일 문자열로 반환했다. 문서 검증기가 거절해 설계 문서를 공개하지 않았고 사업 판단도 나오지 않았다. steps=6, completed=0, suspended=5, resumed=0이다.

문서 필드 타입 지침을 명시하고 문자열 `limitations`를 거절하는 회귀검사를 추가했다. 기존 실패 state·보고서를 수정하거나 성공으로 재분류하지 않았으며 새 state에서 재실행한다. 강제 형 변환으로 모델 출력을 통과시키지 않는다.

두 번째 실행(`target-review-02`)은 첫 대기 turn에서 스트림 재연결이 반복된 뒤 Codex가 실패를 반환했다. 약 213초 동안 heartbeat는 응답했지만 출력은 완료되지 않았다. 기본 시간 제한으로 중단한 것이 아니다. 세 번째 실행은 `--structured-output=false`를 명시한 진단 모드로 진행하며 로컬 문서·의존성·참조 검사는 유지한다. 이는 자동 fallback이 아니며, 결과가 달라도 출력 스키마가 장애 원인이라는 인과관계를 입증하지 않는다.

### 중단 후 진단 (2026-11-18)

실행 03(출력 스키마 미사용)과 04(Codex 0.169.1)도 실패했다. 사용자 요청에 따라 추가 연결 확인용 모델 실행을 취소했고 팀 실행은 재개하지 않았다. 내부 로그에서 실행 02·03·04 각각 `sampling_error=workspace routing discovery timed out` 10건을 확인했다. HTTP fallback 후에도 같은 오류가 발생했다. 여기서 workspace는 프로젝트 디렉터리가 아니라 ChatGPT 계정의 백엔드 라우팅을 의미한다.

Go 어댑터를 거치지 않고 Codex 0.169.1에 직접 `initialize` → `initialized` → `account/read(refreshToken=false)`를 보냈다. 초기화는 성공했지만 계정 조회는 약 15초 후 RPC 내부 오류 `-32603`으로 종료했다. 이 진단에서는 모델 turn을 시작하지 않았다. 계정 조회 오류의 상세 메시지는 수집하지 않았으므로 해당 호출도 동일한 timeout이라고 단정하지 않는다.

[공식 app-server 문서](https://developers.openai.com/codex/app-server/)와 대조하면 어댑터의 초기화, thread 시작·재개, turn 시작 순서는 일치한다. 다만 계정 상태 사전 확인이 없고 서버가 요청하는 외부 인증 토큰 갱신을 지원하지 않는다. 공식 문서상 managed ChatGPT 인증은 Codex가 토큰 갱신을 담당하며 external-token 인증은 호스트가 담당한다. 따라서 갱신 콜백 미구현이 이번 장애 원인이라고 단정할 수 없다.

현재 확인된 것은 계정 라우팅 timeout과 직접 계정 조회 실패다. 정책 거부, 인증 만료, 특정 네트워크 설정 또는 서버 장애 중 어느 것이 근본 원인인지는 확인되지 않았다. heartbeat 성공은 로컬 RPC 생존의 증거이며 원격 계정·모델 서비스 준비 완료를 보장하지 않는다. 현 어댑터의 제한된 오류 메타데이터가 구체적인 실패 원인을 가린 점은 관측성 개선 과제다.

### 계정 조회 후속 진단 (2026-11-18)

사용자가 후속 진단을 승인한 뒤 모델 turn 없이 재확인했다. 로컬 인증 파일의 비밀값을 출력하지 않고 방식과 필드 존재 여부만 확인했으며 `auth_mode=chatgpt`, access/refresh token 및 account ID 존재를 확인했다. 외부 토큰 관리 방식이라고 볼 근거는 없다. 프록시 환경 변수는 발견되지 않았으나 시스템 프록시·VPN 부재까지 확인한 것은 아니다.

| 조건 | 결과 |
| --- | --- |
| 실행 샌드박스 외부, Codex 0.169.1, 직접 account/read | 초기화 성공, 계정 조회 0.78초 성공, chatgpt 계정 및 workspaceRouting 반환 |
| 기본 제한 실행 환경, 같은 진단 | 초기화 이전 프로세스 종료, Operation not permitted (os error 1) |
| 실행 샌드박스 외부, Codex 0.166.0, 직접 account/read | 초기화 성공, 계정 조회 0.40초 성공, chatgpt 계정 및 workspaceRouting 반환 |

두 성공 진단은 기존 인증을 사용했고 재로그인, 강제 토큰 갱신, 전역 설정 변경을 수행하지 않았다. account/read는 refreshToken=false로 호출했다. 각 프로세스는 조회 후 종료했다. 기본 제한 환경의 실행 권한 오류는 초기화와 heartbeat가 성공했던 과거 라우팅 timeout과 실패 단계가 다르므로 동일 원인으로 합치지 않는다. 과거 실패의 실행 환경과 현재 성공 조건이 완전히 같다고 입증하지 못했으므로 서버의 일시 장애였다고도 확정하지 않는다.

현재 계정 조회는 성공하지만 모델 추론과 6역할 파이프라인 복구는 검증하지 않았다. 팀은 중단 상태를 유지한다. 다음 구현 과제는 계정 조회 preflight와 비밀값을 노출하지 않는 오류 분류이며, 그 뒤 최소 모델 호출과 팀 실행을 순서대로 검증할 수 있다.

### 복구 재검증: 실패 재현 (2026-11-18)

사용자 승인 후 기존 `codex-pilot --probe`로 외부 조사 없는 합성 모델 turn 1개를 실행했다. Codex 0.169.1, 워커 1개, prompt JSON 모드, 새 state `target-review-recovery-probe-20261118`을 사용했다. 계정 조회가 다시 15초 후 `-32603: workspace routing discovery timed out`을 반환했고, 모델 실행의 내부 로그에서도 같은 원인을 4건 확인했다. 반복 장애가 확인된 시점에 이번 probe의 부모 프로세스에 SIGINT를 보내 추가 재시도를 중단했다. 이는 모델이 정상 완료한 실패 보고가 아니라 진단 목적 취소이며 팀 실행은 시작하지 않았다.

과거 실패 실행 02·03·04 및 이번 probe의 해당 프로세스 로그에서 `Too Many Requests`, `usageLimitExceeded`, `rateLimitExceeded` 및 일부 HTTP 429 표기를 검색했지만 발견하지 못했다. 로그 검색만으로 서버 내부의 throttling을 배제할 수는 없다. 사용량 조회 `account/rateLimits/read`를 단독으로 호출했으나 진단용 제어 요청 대기 상한 35초 내 응답을 받지 못해 현재 잔여 할당량은 확인하지 못했다. 이 35초는 모델 turn 제한이 아니다. 최초 조회 스크립트의 텍스트 버퍼링 가능성을 제거한 바이트 단위 JSONL reader로도 단독 조회 무응답을 재확인했다.

결론: 계정 조회의 일시 성공은 있었으나 안정적 복구는 확인되지 않았다. 요청 과다로 잠시 차단됐다는 가설은 현재 증거로 확정할 수 없으며, 직접 확인한 장애는 계정 라우팅 탐색 시간 초과다. 추가 모델 호출과 팀 재실행은 중단한다.

### 요청 경로 소스 대조

어댑터는 `exec.Command`로 로컬 Codex를 시작하고 stdin/stdout JSONL로 통신한다. thread 요청의 cwd와 서버 응답 cwd가 다르면 실패 처리한다. 어댑터에는 backend URL이나 계정 라우팅을 지정하는 코드가 없다. 확인한 사용자 config.toml에는 model_provider·chatgpt_base_url·openai_base_url 재정의, forced_chatgpt_workspace_id, custom model_providers가 없었다. 관련 환경 변수 이름 확인에서도 Codex/OpenAI backend URL override는 발견하지 못했다. 이는 모든 설정 계층과 실제 네트워크 목적지까지 검증했다는 뜻은 아니다.

공식 저장소 main의 [account_processor/workspace_routing.rs](https://github.com/openai/codex/blob/main/codex-rs/app-server/src/request_processors/account_processor/workspace_routing.rs)는 `config.chatgpt_base_url`과 현재 인증으로 BackendClient를 만들고 `get_accounts_check()`를 호출한다. 라우팅 준비를 수행하는 read future에 `tokio::time::timeout(Duration::from_secs(15), read)`를 적용하고 초과 시 `workspace routing discovery timed out`을 반환한다. 따라서 이 오류는 잘못된 요청 목적지를 확정하는 메시지가 아니며, 15초는 runtime의 모델 turn 제한이 아니다. main 소스와 설치 바이너리의 완전한 버전 일치는 검증하지 않았으나 설치본의 오류 문자열·스키마·15초 관측과 일치한다.

여기서 계정 workspace와 로컬 cwd는 다른 개념이다. 새 프로젝트 폴더는 파일 격리에 유용하지만 계정 라우팅 장애 해결을 보장하지 않는다. 새 ChatGPT workspace 생성이나 라우팅 주소 강제 변경은 수행하지 않았다.

### 환경 격리 비교 (2026-11-18)

사용자 승인 후 Codex 0.169.1과 같은 인증으로 `initialize` → `initialized` → `account/read(refreshToken=false)`만 순차 호출했다. 모든 실행은 실행 샌드박스 외부에서 수행했고 모델 turn은 0회다. 각 조건은 새 app-server 프로세스를 사용했다.

### 독립 어댑터로 연결 (2026-11-18)

`codex-adapter` 2e2a0da를 공개 저장소에 게시하고 role-runtime은 해당 커밋을 Go 모듈로 직접 의존한다. 로컬 replace는 제거했다. 독립 모듈의 race 테스트·vet, role-runtime의 전체 check가 로컬 연결 상태에서 통과했다. 원격 모듈로 전환한 뒤 전체 `scripts/check.sh`도 통과했다. 독립 어댑터 커밋의 GitHub Actions run 44219363672도 success를 확인했다. 독립 CLI의 실제 `--doctor` 실행은 `-32603 (workspace_routing_timeout)`으로 실패했다. 이 호출은 모델 turn을 시작하지 않았고, 파이프라인 복구 성공으로 기록하지 않는다.

### 실제 호출 성공과 사용자 취소 실행 05

독립 JSON CLI가 Codex 0.169.1로 단일 advisory turn을 완료했고 기대한 `RECOVERY_OK`와 정확히 일치했다. 모델 turn 및 unsubscribe까지 약 3.76초였다. 이어 게시 어댑터를 사용하는 실행 05는 447.45초 동안 4역할 완료, steps=11, suspended=6, resumed=5, maxActive=2, heartbeat=56, 프로세스 2개를 기록했다. 사용자가 goal을 해제하여 SIGINT로 정상 취소했으며 report 오류는 `context canceled`다. 완료된 설계·국내·국제·데이터 문서 4개를 보존했다. 이는 백엔드 실패나 전체 파이프라인 성공이 아니다.

### 실행 06: 소유권 판정 오류

실행 06은 약 421.27초에 데이터 역할의 `heartbeat: expired or superseded execution lease`로 중단됐다. completed=3, suspended=6, resumed=4, steps=10, maxActive=2, heartbeat=53, 프로세스 2개다. 모델 백엔드 재시도는 관찰되지 않았다. 데이터 역할의 마지막 영속 heartbeat는 11:17:19였으며 어댑터의 단조 경과 시간상 약 15초 후 취소됐다. lease TTL은 45초다. 기존 오류 메시지가 만료 시각과 세대 정보를 보존하지 않아 실제 시간 만료·소유권 변경 원인을 확정하지 못했다.

만료 기준과 재실행 정책은 변경하지 않고 Renew/Finish 거절 시점의 세대·상태·now·deadline·lastHeartbeat를 포함하는 LeaseError 진단을 추가했다. errors.Is(ErrStaleLease)와 만료된 실행 거절을 유지하고, 오류 진단 및 거절 후 상태 불변성을 회귀검사한다. 다음 실행에서 동일 조건의 복구를 재검증한다.

### 실행 07: 벽시계 이동 확인과 수정

추가 진단으로 원인을 확인했다. 거절 당시 레코드는 running이고 generation=expected=2였지만, lastHeartbeat=14:20:16, deadline=14:21:01, now=14:35:30이었다. 별도 관찰 프로세스에서도 같은 구간에 wall-clock 949.63초, monotonic 50.63초를 측정해 약 899초의 차이를 확인했다. 이 차이는 시각 조정뿐 아니라 macOS 절전·프로세스 실행 중단 등에서도 나타날 수 있어 원인을 특정하지 않았다. 시스템 시각과 단조 경과의 차이가 왜 발생했는지는 조사 범위 밖이며, 앞선 계정 라우팅 timeout의 원인도 이 증거만으로 설명하지 않는다.

기존 구현은 JSON으로 저장하면서 단조 시계 성분이 사라진 deadline과 현재 벽시계를 비교했다. 수정은 활성 소유자 Store 안에 최대 64개의 단조 시계 deadline을 유지하며 실제 TTL·세대·상태를 검사한다. 파일의 시각은 감사 메타데이터로 유지한다. 완료·대기·격리 시 활성 항목을 해제하고 재시작한 Store에는 활성 소유권을 복원하지 않는다. 따라서 이전 실행을 자동 부활시키지 않고 기존 RecoverCooperative 격리를 유지한다. TTL 45초 자체를 늘리거나 만료 거절을 제거하지 않았다.

회귀검사: 벽시계 +3시간/-3시간 이동에도 정상 소유자 갱신, 실제 경과 시간 만료 거절, 만료된 결과 거절, 세대 불일치 거절, 재오픈한 Store의 이전 lease 갱신 거절 및 불확정 격리. engine race 검사와 vet 통과.

### 2026-11-19: 승인된 직접 진단과 절전 통제

사용자가 공식 계정 조회 주소에 대한 직접 인증 진단을 승인했다. 첫 Python 시도는 URLError였으며, 인증 없는 동일 인터프리터 검사에서 로컬 issuer certificate 오류(code 20)를 확인했다. 인증서 검증을 끄지 않고 `/etc/ssl/cert.pem`을 사용하자 공식 `https://chatgpt.com/backend-api/wham/accounts/check`가 HTTP 200을 약 0.60초에 반환했다. 리다이렉트를 금지했고 토큰·계정 식별자·응답 본문은 출력하지 않았다. 이후 독립 CLI의 `--doctor`도 chatgpt 및 routingAvailable=true로 성공했다. 이 관측은 현재 인증·계정 조회 성공을 입증하며 과거 timeout의 근본 원인을 확정하지 않는다.
