# G1 조사 준비 및 범위 재심

일자: 2026-11-17. 상태: 부문별 조사 준비안 작성 완료. 고객 조사·사업 투자 미승인. 실제 런타임 검증으로 우선순위 변경.

## 스폰서 수정 S1

사용자는 “행사 검색보다는 다양한 이벤트를 한 번에 검색”하는 구상이며 Visit Seoul의 정보 범위는 한정적일 수 있다고 설명했다. 이어 “사업 범위를 좁힌 게 에이전트의 결정이면 그렇게 가도 괜찮다”, “잘 몰라서 물어본 것”이라고 명확히 했다. 이는 다범주 유지 명령이 아니며 에이전트 조직은 근거를 갖고 범위를 결정할 재량을 가진다. 의장이 첫 설명을 즉시 축소 철회 지시로 해석한 것은 성급했다.

D0의 지역 행사 중심 방향을 대안들과 재비교한다. 개발 투자 전 고객 문제·공급·비용 검증이 필요하다는 조건은 유지한다. 범위를 좁힌 이유가 사업 가설인지, 단순한 데이터 접근 편의인지 명시해야 한다.

원래 목적은 **여러 서비스·브랜드·채널에 흩어진 다양한 이벤트와 혜택을 한 번에 탐색하고 원문으로 연결하는 것**이다. 프로모션·할인·증정·응모·팝업·체험·문화행사는 조사 분류의 예시이며 확정된 제품 분류가 아니다. 이 목적을 이해하고 비교한 뒤 특정 지역·범주를 선택하는 것은 허용된다.

Visit Seoul의 기간·키워드 검색은 확인되었지만, 그것만으로 여러 범주의 통합 탐색 요구를 충족한다고 판단하지 않는다. 현재 확인은 [공식 행사 목록](https://korean.visitseoul.net/eventsx)의 기능 존재에 한정된다. 실제 커버리지와 누락 정도는 별도 조사 대상이다.

## 수정된 검증 질문

1. 사용자가 실제로 여러 이벤트 범주와 출처를 오가며 검색하는가? 최근 사례와 행동을 확인한다.
2. 기존 서비스별 제공 범주·출처·조건·기간·지역 범위는 어디까지인가? 없다고 추정하지 말고 관찰 범위와 미확인을 구분한다.
3. 통합 결과가 각 원문 탐색보다 발견·조건 확인·참여 결정에 도움이 되는가?
4. 회원·카드·구매·방문·응모 등의 서로 다른 조건을 정보 손실 없이 표현하고 갱신할 수 있는가?
5. 접근·활용 가능한 공급으로 여러 범주를 유지할 수 있는가? 서로 다른 URL과 독립 공급원을 구분한다.

작은 실험은 여러 범주를 포함하는 층화 표본으로 만든다. 표본 규모를 줄이는 것과 제품 목적을 단일 범주로 바꾸는 것을 구분한다. 범주별 표본 수·미확인·누락을 공개하며 전체 이벤트 커버리지를 주장하지 않는다.

## 실행 방식

G0의 협업 에이전트 3명을 재호출해 고객·마케팅, 데이터·운영, 재무 산출물을 준비하고 사용자 수정사항을 각 부문에 전달했다. role-runtime을 통한 실행은 아니다. 실제 고객 모집·연락·인터뷰, 광고·유료 구매, 7일 추적은 수행하지 않았다.

## 부문 간 비교 및 미해결 사항

[고객·마케팅](g1-customer-marketing.md), [데이터·운영](g1-data-operations.md), [재무](g1-budget.md)가 모두 A(다범주 소규모 비교)를 추천했다. B(특정 진입 범주), C(서울 문화행사)는 금지된 대안이 아니라 다음 근거에 따라 선택할 대안이다. 데이터팀은 10개 후보·4시간 이내 접근성 검토를 다음 사전 단계로 제안했다. 실제 10개 후보 검증은 수행하지 않았다.

예산 충돌은 해결되지 않았다. 고객·마케팅 22시간 40분(설계 포함), 데이터·운영 11~23시간을 단순 합산하면 33시간 40분~45시간 40분이며, 재무 기준안의 전체 24시간을 초과한다. 설계·공동 보고 중복분을 제거해도 같은 예산에 들어가는지 아직 확인하지 않았다. 고객안 23일과 재무안 21일도 조정 대상이다. 따라서 전체 8명·30항목·7일 조사는 실행 준비 완료로 판정하지 않는다. 부문 예산표는 확정안이 아닌 서로 비교할 제안으로 남긴다.

## 새로운 안건과 실행 우선순위

사용자는 Welcome to Korea라는 국내 여행 탐색안을 제시했다. 자동 공급은 공공기관에 한정하고, 민간은 직접 등록·광고로 수익화하는 가설이다. 범위·수익 주체가 구체화되었으나 고객·광고 수요는 미검증이다.

이어 사용자가 “검증 대상은 런타임인데 어댑터가 필요하지 않은가”라고 지적했다. 협업 에이전트 회의를 계속하는 대신 실제 Codex 어댑터를 구현하고 이 새 안건을 실제 Pool의 검토·반론·의장 작업으로 공급하도록 우선순위를 바꿨다. [실행 계약](../../docs/design/codex-adapter.md)을 따른다. 앞의 협업 회의 기록을 런타임 실행 증거로 소급하지 않는다.
