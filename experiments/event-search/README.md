# 사업 제안부터 시작하는 조직 실험

상태: 전체 조직 설계 및 일부 파일럿 실행. 실제 고객 조사·사업 예산 승인은 아니다.

첫 [G0 파일럿](g0-pilot.md)은 협업 에이전트로 별도 실행했다. 이후 [Codex 어댑터](../../docs/design/codex-adapter.md)로 고객·재무·운영·의장 4개 역할의 실제 Pool 실행을 추가했다. 아래 전체 40역할 조직은 아직 실행 전이다.

현재 사업 범위와 새 Welcome to Korea 안건은 [G1 재심 기록](g1-decision.md)을 따른다. 사용자 의도를 이해한 뒤 근거에 따라 범위를 좁히거나 변경하는 재량은 팀에 있다.

이벤트·혜택 검색을 출발 가설로 삼아 사업 제의 → 독립 검토 → 반론 → 투자 심의 → 고객·시장 검증 → 제품 설계 → 개발 → 출시 검증을 진행한다. 개발 착수, 검색엔진 형태, 수익 모델은 미리 확정하지 않는다. 유용한 근거가 나오면 대상 고객·제품 형태·사업 방향을 변경하거나 중단할 수 있다.

사용자는 사업 스폰서다. 에이전트 임원진은 실험 안에서 결정을 내리며, 실제 지출·광고 집행·외부 연락 권한을 임원 직함만으로 얻지 않는다. 실험 예산안과 실제 모델 실행 비용은 별도 장부로 기록한다.

## 조직

40개는 영속 역할 컨텍스트 수다. 초기 동시 실행 슬롯은 4개로 설정하되 최적값으로 주장하지 않는다. 회의 참석자마다 프로세스를 상주시키지 않는다. 필요한 심의 안건만 실행하고, 답변을 기다리는 역할은 체크포인트를 남겨 슬롯을 반환한다.

| 부문 | 역할 ID와 담당 | 책임 산출물 |
| --- | --- | --- |
| 경영·전략 | executive-chair 의장, strategy-lead 전략, business-sponsor 사업 제안자, portfolio-reviewer 투자 대안 검토, chief-of-staff 의사결정 기록 | 제안서, 대안 비교, 결정 기록 |
| 재무 | finance-lead 재무 책임, fp-and-a 예산, unit-economics 단위 경제성, procurement 조달 | 범위별 예산안, 비용 가정, 중단 조건 |
| 고객·시장 | research-lead 조사 설계, customer-research 고객 문제, market-research 시장, competitive-research 경쟁, research-auditor 근거 검토 | 조사 계획, 출처 장부, 검증된 문제 |
| 마케팅·사업 | marketing-lead 마케팅 책임, positioning 포지셔닝, acquisition 획득 전략, lifecycle 재방문, partnerships 제휴 | 고객군별 메시지, 채널 실험, 수익 가설 |
| 제품·디자인 | product-lead 제품 책임, product-planner 범위 설계, ux-research 사용성, service-design 서비스 흐름, visual-design 화면 | 버전이 있는 요구사항·설계·수용 기준 |
| 기술·데이터 | tech-lead 기술 책임, architecture 구조, data-architecture DB, ingestion 수집, search 검색, backend-service 서비스·DTO, api-integration 컨트롤러, frontend UI | 기술 타당성, 구현, 데이터 계약 |

각 역할에는 지침 외에 목표, 평가 기준, 검토 권한, 필요한 입력, 산출물, 열린 질문을 둔다. 예를 들어 마케팅은 고객 도달성과 차별성을, 재무는 현금 소요와 민감도를, 기술은 수집·갱신 가능성과 운영 비용을 평가한다. 반대를 의무화하거나 직함에 맞춘 연기를 시키지 않는다. 같은 모델의 여러 역할은 독립된 전문가 집단이라는 보장이 없으므로 출처와 재현 가능한 검증으로 판단을 보완한다.

## 첫 안건: 이 사업을 조사할 가치가 있는가

첫 산출물은 앱이 아니라 다음의 의사결정 묶음이다.

1. 사업 제안자: 고객 문제, 현재 대안, 기대 가치, 검증이 필요한 가설을 제출한다. 시장 규모·수익·수요를 임의로 사실화하지 않는다.
2. 고객 조사·마케팅·재무·기술·데이터 이용 조건 담당: 서로의 결론을 보기 전에 독립 검토서를 작성한다.
3. 기록 담당: 주장별 근거와 상충 지점을 연결한다. 중복된 의견을 표 수로 계산하지 않는다.
4. 담당자: 중요한 반론에 답하고 제안을 수정한다. 최초 의견과 수정 이유를 보존한다.
5. 의장: 진행 / 조건부 진행 / 추가 조사 / 방향 전환 / 중단 중 하나를 선택하고 근거·소수 의견·재검토 조건을 기록한다.

기본 논의 한도는 독립 검토 1회와 반론·수정 2회다. 해결되지 않은 핵심 사실은 다수결로 참으로 만들지 않고 추가 조사 또는 보류로 끝낸다. 하위 결정은 해당 책임자에게 위임하고, 목표 고객·수익 방식·예산 한도 변경은 임원 심의 대상으로 올린다.

## 예산안과 단계별 심의

| 단계 | 결정 질문 | 필요한 결과 |
| --- | --- | --- |
| G0 제안 심의 | 조사할 가치가 있는가? | 고객 문제 가설, 대안, 미확인 사항, 조사 예산안 |
| G1 발견 단계 | 누구의 어떤 문제를 해결할 것인가? | 근거 있는 고객·시장 분석, 데이터 공급 가능성, 마케팅 가설 |
| G2 투자 심의 | 어떤 범위를 얼마 동안 검증할 것인가? | 최소·기준·확대 예산 시나리오, 범위, 성공·중단 기준 |
| G3 제품 검증 | 구현이 가설을 시험하는가? | 설계, 구현, 독립 QA, 비용·품질 결과 |
| G4 출시 심의 | 출시·수정·중단 중 무엇이 합리적인가? | 운영·마케팅 실험안, 잔여 위험, 검증 결과 |

예산 항목은 모델 사용, 데이터 확보, 인프라, 인력 환산, 마케팅으로 구분한다. 각 수치에는 통화·기간·수량·단가·출처·추정 범위·제외 항목을 붙인다. 실제 견적이 없으면 `unknown` 또는 명시적 가정으로 남긴다. 투자 수익을 만들어 내기 위해 가상의 고객 조사나 매출을 꾸미지 않는다.

## 토론·메시지·결정 계약

- 검토서: `id`, `revision`, `role`, `question`, `position`, `evidence_refs`, `assumptions`, `alternatives`, `risks`, `requested_checks`, `supersedes`.
- 근거: 출처 URL/파일, 확인 날짜, 관찰 내용, 적용 한계. 관찰·추정·제안·미확인을 구분한다.
- 결정: `id`, `revision`, `owner`, `input_revisions`, `outcome`, `rationale`, `dissent`, `conditions`, `reopen_trigger`, `supersedes`.
- 작업: 책임 역할, 입력 산출물 버전, 선행 조건, 완료 조건, 실행 예산, 결과 참조. 문서 전체를 모든 역할에게 배포하지 않는다.
- SMS: 검토 요청·반론·답변·결정 통지에 사용한다. 원문은 버전이 있는 산출물 저장소에 두고 메시지에는 참조와 요청을 보낸다. 현재 메일박스의 불변 correlation 슬롯에 맞춰 안건·회차·요청별 correlation을 새로 만든다.
- 방향 변경: 이전 결정을 덮어쓰지 않는다. 영향을 받는 후속 작업을 보류하고 입력 버전을 갱신해 다시 접수한다. 이미 실행 중인 작업의 취소·오래된 결과 거절은 외부 조정 계층에서 구현·검증해야 한다.

전체 논의 이력을 매 실행에 주입하지 않는다. 공통 사업 헌장, 해당 역할의 체크포인트, 이번 안건의 입력 버전, 관련 근거·미해결 반론으로 컨텍스트를 구성한다. 이 방식은 명시적 문서 선택이며 DB 토큰 페이징 구현을 의미하지 않는다.

## 구현 순서와 검증

1. 실행 연결: 실제 모델 하네스 어댑터의 시작·완료·취소·역할 복원 및 사용량 계측을 작은 작업으로 확인한다. 현재 pi 합성 공급자 검증만으로 실제 조직 실행을 주장하지 않는다.
2. G0 파일럿: 사업 제안과 5개 관점의 검토, 반론, 의사결정 한 건을 실행한다. 40개 역할 전체의 활동을 의무화하지 않는다.
3. 회귀 시나리오: 근거 없는 수요 수치, 답변 지연, 모순된 근거, 예산 초과안, 방향 변경을 넣어 보류·재검토·대기 슬롯 반환을 검증한다. 실행 중 장애는 현재 런타임 정책대로 격리하며 자동 복구를 주장하지 않는다.
4. G1 이후: G0 결과에 따라 조사·마케팅·예산 업무를 공급한다. 제품 구현은 G2에서 정한 범위로 진행한다.
5. 비교 실행: 순차 실행 / 일반 제한 동시 실행 / role-runtime의 영속 역할 실행에 동일한 초기 안건·근거 묶음·모델·예산·평가 기준을 적용한다. 방향은 달라질 수 있으므로 최종 기능 수만으로 비교하지 않는다.

측정 항목은 결론의 근거 추적률, 주요 반론 처리율, 미확인 사실을 사실로 쓴 건수, 오래된 입력을 사용한 결정 수, 완료 품질, 재작업, 비용·토큰, 처리 시간, 대기 중 슬롯 점유, 최대 활성 워커, 재개 시 상태 보존이다. 실제 고객 수요의 입증과 에이전트 조직의 실행 성공은 별도로 평가한다.

역할·안건 선택과 의사결정 절차는 외부 조직 조정 계층의 책임이다. Go 런타임의 역할 활성화·워커 제한·메시지·체크포인트 기능과 분리한다. 이 문서는 그 조정 계층의 요구사항이며 아직 실행 가능한 스케줄러나 역할 정의 파일이 아니다.
